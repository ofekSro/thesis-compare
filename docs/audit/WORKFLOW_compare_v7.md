# עבודה שוטפת עם ה-skills ב-compare_v7

העבודה ב-compare_v7 בנויה סביב חמישה skills: `/decide`, `/verify`, `/tidy`, `/worklog` ו-`/ref`.
כולם קוראים את ה-`CLAUDE.md` של הפרויקט, ולכן אף אחד מהם לא משנה קובץ בלי אישור מפורש.

## מחזור עבודה רגיל

### 1. פתיחת שיחה

פותחים את compare_v7 ב-Claude Code ומתחילים ב:

```
/decide status
```

מתקבלת תמונת מצב: מה פתוח, מה בתוקף, ואילו מספרים ביומן כבר הוחלפו.
זה מחליף את הקריאה הידנית של ה-HANDOFF.

אפשר להוסיף גם:

```
/verify status
```

מה פתוח מהביקורת האחרונה, לפי טבלת ה-carry-over שלה ולפי הרישום.
חיפוש ב-git log משמש רק כמקור משני.

### 2. בחירת עבודה

בוחרים החלטה פתוחה או ממצא מה-audit, ופועלים לפי הסוג.

**החלטה מחקרית חדשה**, כמו סף, קריטריון או צורת מודל:

```
/decide open רצפת הלחץ למדרגות נזק
```

מנסחים יחד את השאלה ההנדסית, העוגנים, החלופות וכלל ההכרעה במספרים.
רק אחרי אישור מריצים מדידות.

**ממצא עם תיקון מוגדר**, כמו באג או קבוע שמוגדר פעמיים:

```
/verify fix PHY-03
```

מסביר מה ישתנה ומה יזוז, מחכה לבחירה, מבצע, ומראה diff ותוצאות בדיקות.
אם התיקון דורש בחירה בין חלופות, הוא מתחיל אוטומטית ב-`/decide open`.

**קוד שצריך סדר והערות:**

```
/tidy blastlib/processing
/tidy apply blastlib/processing/grids.py 2 5
```

קודם הצעה ממוספרת לכל קובץ. אחר כך ביצוע רק של הפריטים שנבחרו, עם השוואה מספרית לפני ואחרי שחייבת לצאת אפס.

### 3. בדיקת ההחלטה אחרי שבוצעה

```
/decide check D8
```

המבקר העוין בודק שלושה דברים, לפי הסדר:

1. האם ההחלטה עונה על השאלה ההנדסית שלי.
2. האם היא מכבדת את העוגנים שלי.
3. האם הראיות והחוסן תומכים בה.

הוא מעלה רק התנגדויות שעשויות לשנות את ההחלטה או מספר שמצוטט.
כל התנגדות מסתיימת ב"מה היה משנה את דעתי".

### 4. סגירת שיחה

```
/worklog draft
/worklog
```

קודם מסתכלים על הטיוטה ומתקנים, ואז כותבים.
הרשומה מפנה למספרי ה-D שהשתנו.

## בדיקות תקופתיות

| מתי | פקודה | מה זה נותן |
|---|---|---|
| אחרי שינוי גדול בקריטריון או במודל | `/verify` | חמש עדשות במקביל ו-SUMMARY חדש בתיקיית תאריך. הוא נפתח בטבלת carry-over: מה מהביקורת הקודמת נפתר, מה פתוח, מה תוקן חלקית, מה חזר ומה נסגר בהחלטה |
| אחרי `/verify` חדש | `/decide index` | ממצאים חדשים שדורשים הכרעה נכנסים לרישום |
| אחרי שינוי שמזיז מספרים | `/verify repro` | בדיקה שהטבלאות משוחזרות מהקוד ב-commit הנוכחי |
| לפני כתיבת פרק בתזה | `/verify trace <נתיב לקובץ tex>` | מיפוי כל מספר בפרק לקוד, לבדיקה ולטבלה |
| לפני כתיבת פרק או תיקון המאמר | `/decide status` | אילו מספרים הוחלפו ואסור לצטט |

דוגמה ל-trace:

```
/verify trace "C:\Users\rotem.ofek\OneDrive - Technion\תואר שני\תזה\Thesis_Writing\Content\9.ParametricStudy.tex"
```

הנתיב המפורש הוא האישור לקרוא מחוץ לתיקיית הפרויקט.

## כללים שכדאי לזכור

- **כל שינוי עובר דרכי.** skill שמגיע לשלב ביצוע עוצר, מסביר מה ישתנה ומה יזוז, ומחכה. "נשמע טוב" לא מספיק. צריך לבחור אפשרות בשמה.
- **commit ו-push הם שני אישורים נפרדים.**
- **צינור הייצור** (בערך חצי שעה) רץ רק כשאני מבקש. הסוכנים מריצים לבד רק את הבדיקות המהירות והצינור הקצר.
- **ביקורת חדשה ממשיכה את הקודמת.** כל סוכן קורא את הביקורת האחרונה שיש בה SUMMARY ואת `docs/DECISIONS.md`. ממצא ישן שומר על המזהה שלו, וממצא חדש ממשיך את המספור (למשל ALG-21). הסטטוס נקבע לפי הקוד של היום, לא לפי הרישום. אם הרישום והקוד לא מסכימים, זה ממצא. החלטה שבתוקף לא עולה שוב, אלא אם יש ראיה חדשה נגד השאלה או העוגנים. במקרה כזה הממצא מסומן "challenges D#". ביקורות ישנות לא נמחקות.
- **כשאני לא מסכים, אני אומר את זה.** אחרי שני סבבים Claude אמור לעצור ולומר "ייתכן שאנחנו מחפשים דברים שונים", ולהציג את החלופות זו לצד זו. אם זה לא קורה, להזכיר לו.
- **נסיגת מודל.** אם Fable 5 לא זמין או מסרב, הסוכנים עוברים ל-Opus 5.5 ומודיעים על כך.

## צעד ראשון מומלץ

1. לשמור ב-git את `WORKLOG.md` ואת `docs/audit/2026-09-28/D13_UNITS_DECISION_HE.md`, שעדיין לא נשמרו.
2. `/decide index`, כדי לאחד את D1 עד D18 מכל המקורות לרישום אחד.
3. להשלים שאלה ועוגנים להחלטות החשובות, קודם כול לקריטריון האימפולס.
4. `/decide check` על קריטריון האימפולס.
